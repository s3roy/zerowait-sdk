Zerowait docs

Zerowait keeps your app's web screens warm, so they open the moment someone taps: checkout, a help centre, onboarding or KYC, a live stream, a mini-app, a video call.

Your app stays native. The screens that are web pages open already loaded and signed in, on the route you ask for, instead of starting from a blank page. When the screen closes, it is ready again for the next time.

Requirements

AndroidAndroid 8.0 (API 26) or later. An up-to-date Android System WebView (any updated in the last few years). Kotlin or Java.
iOSiOS 15 or later. Xcode 27.2 or later (the binary is built with it). Swift or Objective-C apps. See iOS.
Web appAnything that runs in a browser. In-place route changes need Next.js or a one-line hook; other pages still open faster because the engine and cache are warm.

Install

Android

Add the Zerowait Maven repository and the dependency. Its dependencies (AndroidX WebKit) come with it.

// settings.gradle.kts
dependencyResolutionManagement {
    repositories {
        google()
        mavenCentral()
        maven("https://s3roy.github.io/zerowait-sdk/maven")
    }
}

// app/build.gradle.kts
dependencies {
    implementation("dev.zerowait:zerowait:0.3.1")
}

Prefer a file? Download zerowait-0.3.1.aar, put it in app/libs/, and add implementation(files("libs/zerowait-0.3.1.aar")) plus implementation("androidx.webkit:webkit:1.12.1").

iOS

In Xcode: File → Add Package Dependencies, enter https://github.com/s3roy/zerowait-sdk, and add the Zerowait product to your app. Or in Package.swift:

.package(url: "https://github.com/s3roy/zerowait-sdk", from: "0.3.1")

Add NSCameraUsageDescription and NSMicrophoneUsageDescription to Info.plist only if a web screen uses the camera or microphone.

Android permissions

The library manifest adds INTERNET, plus CAMERA, RECORD_AUDIO and MODIFY_AUDIO_SETTINGS for pages that use media. Camera and microphone hardware are marked optional, so your Play Store availability does not change. Remove them with tools:node="remove" if no web screen of yours uses media.

Quick start

1. Register and prewarm when the app starts

class MyApp : Application() {
    override fun onCreate() {
        super.onCreate()
        Zerowait.register(this, "checkout", WarmPageConfig(
            warmUrl = "https://shop.example.com/cart",
            cookies = listOf(PageCookie("session", Session.token)),
        ))
        Zerowait.prewarm(this, "checkout")   // runs when the main thread is next idle
    }
}

Prewarming waits for the main thread to go idle, so it does not delay your first frame. If the user logs in later, register or call setCookies after login and prewarm then.

2. Open it from any screen

class CheckoutActivity : ComponentActivity() {
    private lateinit var page: WarmPage

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        val container = FrameLayout(this)
        setContentView(container)
        page = Zerowait.open(this, "checkout", container, "https://shop.example.com/checkout?step=pay")
    }

    override fun onDestroy() {
        if (isFinishing) page.close()   // back to the warm page for next time
        super.onDestroy()
    }
}

That is the whole integration for a Next.js app. For other frameworks, add the one-line hook.

All WarmPage and WarmPool methods run on the main thread, and listeners are called on the main thread.

License key

Set your key once at launch, before opening any page:

// Android: Application.onCreate
Zerowait.license(this, "ZW1.…")
// iOS: AppDelegate, application(_:didFinishLaunchingWithOptions:)
Zerowait.license("ZW1.…")
  • The key is checked inside the app, offline, against your package name (Android) or bundle id (iOS). Nothing is sent anywhere.
  • Nothing is ever blocked. With no key, debug builds (iOS: Simulator or development signing) only log a warning, and release builds show a small "Zerowait · unlicensed" label on Zerowait screens. A key that is present but not valid (expired for this SDK version, another app id, mistyped) shows the label in debug builds too, so you see it before you ship.
  • A key lists your app ids (for example com.acme.app, or com.acme.* for every id under it) and an "updates until" date. It covers every SDK version released up to that date and never stops working in an app you have shipped.
  • To check your setup, pass strict = true (iOS: strict: true): the label then shows in debug builds too. Zerowait.licenseStatus tells you why a key is rejected: missing, malformed, bad signature, app id not covered or updates expired.
  • Keep the key in your app's code or build config. It only works for your app ids, so it is not a secret, but don't publish it.

How a warm page works

Each WarmPage is one web screen. Zerowait.register and Zerowait.open use a shared WarmPool; create a WarmPage yourself when you want full control.

Idle ── warm() ──▶ Warming ── warm page loaded ──▶ Ready Ready ── open(container, url) ──▶ Open Open ── close() ──▶ Closing ── leave confirmed ──▶ Ready (back on warmUrl) any ── browser crash ──▶ Idle ──▶ warm() again, by itself

open() always works, whatever the state. What it costs depends on where the page is:

lastOpenModeWhenWhat happened
"soft"Ready, same origin, the app can change routeRoute change inside the running app. Fastest.
"load"Still warming, other origin, or no router hookNormal page load, still faster than without Zerowait.
"cold"Never warmedNothing prepared. This is what an app without Zerowait does.

Because a page that was never warmed still opens, you can compare both paths with the same code: warm one, don't warm the other.

A warm page that is not on screen is silent: audio or video it tries to play waits until its screen opens, and stops when the screen closes.

Opening a route without a reload

The softNavigateJs option decides how your web app moves to the URL you open. The default, SoftNav.AUTO, works with:

  1. Next.js (pages router and app router). Nothing to add.
  2. A hook your app defines. One line, for React Router, Vue Router, Angular, SvelteKit or anything else: 
    // React Router
const navigate = useNavigate();
window.__zerowaitNavigate = (path) => navigate(path);

// Vue Router
window.__zerowaitNavigate = (path) => router.push(path);
  3. Anything else: a normal load of the URL, still faster than without Zerowait.

Other choices: SoftNav.NEXT_JS, SoftNav.HISTORY (for routers that follow browser history, when you cannot add the hook), your own JS function, or null to always load.

To have the next screen's code ready, prefetch it when the warm page is ready:

WarmPageConfig(
    warmUrl = "https://app.example.com/home",
    afterWarmJs = "window.next?.router?.prefetch('/checkout')",
)

Login and cookies

Cookies in WarmPageConfig.cookies are written before the first load and are readable from document.cookie. Use them to hand the web app the user's session and anything else it reads at start-up, such as the client type or locale.

val cookies = listOf(
    PageCookie("session", session.token),
    PageCookie("client", "android-app"),
    PageCookie("locale", "en-GB"),
)
page.setCookies(cookies)   // after login, no need to warm again

A cookie goes to the warm page's origin unless you give it a url. Values are written as given, so encode them the way your web app decodes them.

Leaving a screen

Some screens must finish something before they go: end a call, save a draft, cancel an order hold. leaveJs runs when you call close(); leaveDoneJs is polled until it is true (or leaveTimeoutMs passes) before the WebView is reused or destroyed.

WarmPageConfig(
    warmUrl = "https://app.example.com/home",
    leaveJs = "performance.clearResourceTimings(); window.saveDraft?.()",
    leaveDoneJs = "performance.getEntriesByType('resource').some(e => e.name.includes('/api/drafts') && e.responseEnd > 0)",
)

Waiting on the request rather than on the UI matters: buttons often disappear at once while the request is still in flight. close(onDone) tells you when it is finished.

Several pages and memory

Each warm page costs memory. WarmPool keeps several named pages and a cap on how many stay warm. When a new page is warmed past maxWarm, the least recently used idle page is released. A page on screen is never released.

val pool = Zerowait.pool(this, maxWarm = 2)
pool.register("checkout", WarmPageConfig("https://shop.example.com/cart"))
pool.register("help", WarmPageConfig("https://help.example.com/"))
pool.register("live", WarmPageConfig("https://live.example.com/lobby"))

pool.warm("checkout")          // warm what the user is most likely to open next
pool.open("help", container, "https://help.example.com/article/42")

override fun onTrimMemory(level: Int) {
    if (level >= TRIM_MEMORY_RUNNING_LOW) pool.releaseIdle()
}

Unknown URLs: the spare engine

When you can't know the URL in advance (links in messages, ads, partner pages), keep a spare engine. Any URL then opens faster than from scratch.

Zerowait.register(this, "any", WarmPageConfig.spare())
Zerowait.prewarm(this, "any")
// later
Zerowait.open(this, "any", container, linkUrl)   // lastOpenMode == "load"

After close() the spare engine goes back to blank and clears its history.

Measuring time to screen

marks names milestones as text that appears on screen. Zerowait reports the moment each one first becomes visible, so you can time tap to screen without changing the web app.

WarmPageConfig(
    warmUrl = "https://shop.example.com/cart",
    marks = mapOf("pay" to "Pay now|Payment method"),
)

page.addListener(object : WarmPageListener {
    override fun onMark(name: String, atElapsedRealtime: Long) {
        analytics.log("screen_ready", mapOf("ms" to atElapsedRealtime - tappedAt, "mode" to page.lastOpenMode))
    }
})

Your page can also report its own milestones: ZerowaitPage.postMessage(JSON.stringify({mark: "ready"})). The bridge exists only on trusted origins.

Serving local pages

intercept lets you answer requests yourself: bundled pages, an offline fallback, or a single-page app shell served from assets for every route.

WarmPageConfig(
    warmUrl = "https://appassets.androidplatform.net/help/",
    intercept = { req ->
        if (req.url.path?.startsWith("/help") == true)
            WebResourceResponse("text/html", "utf-8", assets.open("help/index.html"))
        else null
    },
)

Permissions and security

  • Trusted origins are the warm page's origin plus trustedOrigins. Only they get the bridge, the marks script and camera or mic.
  • Camera and microphone are granted to a page only when its origin is trusted, every requested resource is camera or mic, and your app already holds the matching Android permission. Anything else is denied. Ask for permissions natively before opening a screen that needs them.
  • The page bridge (ZerowaitPage) exists only on trusted origins.
  • Debugging (chrome://inspect) is off unless you set webContentsDebugging. Keep it off in release builds.

Renderer crashes

The system can stop a web page's browser process under memory pressure, or it can crash. Your app keeps running, and Zerowait warms the page again by itself.

Multiple processes

If your app uses WebView in more than one process, each extra process needs its own data directory, or the second one crashes on start:

if (getProcessName().endsWith(":web")) {
    WebView.setDataDirectorySuffix("web")
}

Cookies are per data directory, so set them in each process.

Testing your integration

  • Assert lastOpenMode == "soft" to prove a screen opened without a reload.
  • Set a value on the warm page (window.__probe = 1), open your screen, and read it back: the same value means the same document.
  • Use marks to wait for the screen to be visible, and compare a warmed page with one that was never warmed.

Every release is tested end to end on Android and iOS with a bundled single-page app, a hosted Next.js app and the video call module.

Video call module

For apps with video calls, CallEngine is a ready-made call screen that opens instantly: call states, signaling through your own channel, call audio and stats.

// Application.onCreate
Zerowait.prewarmCall(this)

// Call screen
val engine = Zerowait.engine(this)
callView.attach(engine)            // the loaded page moves in, no reload
engine.signaling = MySignaling(roomId)
engine.startCall(CallOptions(role = CallOptions.Role.CALLER))

If your call screen is already a hosted web page (a meeting or room route in your web app), you don't need this module: use a warm page and open the call route.

Idle ── warm() ──▶ Warming ── page loaded ──▶ Ready Ready ── startCall() ──▶ Connecting ──▶ Connected Connected ── hangup() / remote bye ──▶ Ended ──▶ Ready any ── error / renderer gone ──▶ Failed ──▶ Ready
  • A call started while Warming is queued and starts as soon as the page is ready.
  • CallView shows the call, with a native overlay until it connects; setOverlay(view) replaces it. It survives rotation.
  • CallPermissions.missing(context, media) lists the runtime permissions to request first.
  • For tests: CallOptions.Mode.LOOPBACK, CallOptions.Media.SYNTHETIC and InMemorySignaling.pair() run real calls without a server or camera.

Signaling

Zerowait passes the call's connection messages to a SignalingChannel you implement and feeds incoming messages back. Relay them as they are; you can connect the channel before the call screen opens.

class MySignaling(private val room: String) : SignalingChannel {
    private val socket = MySocket.connect("wss://signal.example.com/$room")
    private var listener: ((JSONObject) -> Unit)? = null

    init { socket.onMessage { text -> listener?.invoke(JSONObject(text)) } }

    override fun send(message: JSONObject) = socket.send(message.toString())
    override fun setListener(listener: ((JSONObject) -> Unit)?) { this.listener = listener }
    override fun close() = socket.close()
}

One side starts with Role.CALLER; the other with Role.CALLEE. Pass ICE servers per call with CallOptions(iceServers = …).

iOS

The iOS SDK has the same model and names as Android, in Swift: Zerowait.register / prewarm / open, WarmPage, WarmPool, SoftNav, and the video call module (CallEngine, CallView). Pages need no iOS-specific code: the same window.ZerowaitPage bridge and __zerowaitNavigate hook work on both.

import Zerowait

// AppDelegate
Zerowait.license("ZW1.…")
Zerowait.register("help", WarmPageConfig(
    warmURL: "https://help.example.com/",
    cookies: [PageCookie(name: "session", value: token)]
))
Zerowait.prewarm("help")          // when the main run loop is next idle

// On tap, in any view controller
Zerowait.open("help", in: containerView, url: "https://help.example.com/article/42")

// When that screen goes away
Zerowait.page("help").close()     // back to warm for next time

// Video calls
Zerowait.prewarmCall()
callView.attach(Zerowait.engine())
try Zerowait.engine().startCall(CallOptions(mode: .relay, role: .caller))

Platform notes:

  • Local pages: iOS cannot serve http(s) requests from your app. Serve bundled pages from a custom scheme (add a WKURLSchemeHandler with configure) or from a server.
  • Memory: on a memory warning, WarmPool frees idle pages by itself.
  • Call audio: manageAudio is off by default; iOS sets the audio session when the page uses the microphone.

Measured on the iOS 27.2 Simulator, a warm help-centre article opened in 82–200 ms against 430–610 ms without Zerowait. For the bundled video call page the gain on iOS is small or none (1.1–1.7 s to the first frame either way across runs), because most of that time is the WebRTC connection itself, not the page.

Limits

  • A warm page uses memory and, for hosted pages, network at warm time. Warm what users are likely to open next, and cap it with WarmPool.
  • In-place route changes need Next.js, the one-line hook, or a router that follows browser history. Other pages still open faster, but load as a page.
  • One WarmPage shows one screen at a time.
  • The video call module does not include signaling, TURN or media servers, and calls do not continue in the background yet.
